## Methodology fixes (important — they invalidate earlier numbers)

1. **Non-determinism**: runs with `seed=42` were not reproducible — the trainer iterates string-keyed `set`s, and `PYTHONHASHSEED` randomization changed their iteration order. Pinned `PYTHONHASHSEED=0` (harness re-execs itself); runs are now bit-identical.
2. **Step-loop bug**: prior benchmark scripts break on `all(e.done)`, skipping the learning step — they measured a non-learning agent. The new harness breaks only on `episodeDone`.
3. **`CoreStackingError`**: intermittent, but **now 0 failures** on the current tree (Deep-1's crash fixes present).

## Findings (corrected)

1. **A2C is not a clear win at matched LR** — it's a *tradeoff*:
   - A2C produces **much denser plans** (fill 36.8% vs 27.0%, placements 28 vs 19.5) and a **higher mean score** (36.7 vs 31.2).
   - PPO has a **higher final-50 score** (37.6 vs 34.2) and uses **~1.8× less memory** (923 vs 1659 MB) and ~2× less wall-clock.
   - The earlier "A2C +14% final score" was a **confound**: the first `a2c_lr001` run (final-50 39.7) was on an *older* tree before Deep-1's changes landed. On the current tree it's 34.2.

2. **§2 is inert** — bit-identical to baseline (0/2994 fields differ). Correct fix, no measurable effect.

3. **A2C at `lr=0.003` collapses** (~ep175) — the REINFORCE loss is ~10× larger magnitude (scales with `log π`), so the default LR is too aggressive. `lr=0.001` is stable.

**The 4–6s spike episodes are candidate-generation explosions on dense sites.** When the RL fills a large/irregular site, `generate_candidates` iterates many attachment edges × slot tiles × rotations × 2 anchors each, and the early-break never fires until `cat_limit` (12) valid candidates are found — so the anchor loop runs wide. Inside it, `cgOverlapCollisions` is the largest sub-cost; the overlap path is NOT naive O(n²) — it already has `_nearby_placement_ids` (spatial index) + `_bounds_intersect` (bbox pre-check) + native-ctypes `polygons_overlap`.

## Memory: it is NOT a leak — it's a bounded plateau

Clear caches every 50 eps via `G.clear_geometry_caches()`, but **`lru_cache.cache_clear()` drops the LRU entries without returning the native ctypes buffers to the OS**. Confirmed with `diag_memory.py` (benchmark for diagnostics): at ep 50 cache sizes fell to ~0 (poly 381/4096, ovl_pk 1/8192, segs 0/1024) while current RSS *rose* 1066→1070 MB. The allocator/malloc arena retains the freed buffers.

So each algorithm reaches a **per-workload plateau** and stays flat (a2c_lr001: 1658.8 MB from ep 250→500; ppo_lr001: ~923 MB from ep 325→500). The A2C vs PPO gap (1659 vs 923) is **workload, not leakage**: A2C produces denser plans (28 placements vs 19.5/ep) → more polygons/segments/overlap-pairs cached → larger arena. No OOM risk from the plateau; it is bounded.

## Two free candidate-gen wins — landed, behavior-neutral by construction

`_candidate_from_anchor` (server.py) had two pure no-ops, now removed:
1. `G.translate_polygon(rotation_poly, anchor_x, anchor_y)` was called twice (identical `poly` reassignment).
2. `_candidate_features(...)` was computed and then **always overwritten** by `_materialize_candidate` (which also rasterizes cells for the daylight proxy). The result was never consumed — now `features=[]` placeholder.

Both are provably metric-neutral: `translate_polygon` and `_candidate_features` are pure (no RNG, no `self` mutation), and the discarded feature vector was overwritten before any consumer. Smoke test (3 episodes) ran clean.

## Batched-C collision path — correct but a NET SLOWDOWN (do not wire in)

Prototyped `polygons_overlap_any_c` (`fast_geometry.c`) + `_native_polygons_overlap_any` (`geometry.py`) + `benchmarks/micro_bench_batch_overlap.py`. It collapses N per-pair `polygons_overlap_c` ctypes round-trips into one native call.

Result: **correct (250/250 agree with per-pair) but 0.52x–0.92x slower** across nearby sizes {1,2,4,8,16,40}. The native SAT is cheap (~µs for 4–8-vertex polys), so the ctypes call overhead was never the bottleneck. The per-pair path already caches placed polys via `_packed_polygon_from_signature`'s `lru_cache`; the batch wrapper rebuilds a fresh flat `_CPoint` buffer every candidate, costing more than the calls it removes.

**Conclusion**: "batch the predicates in C" does NOT achieve full-coverage-without-explosion. The real per-candidate cost is Python-side signature/packing + the `_nearby_placement_ids` spatial query + the anchor-loop breadth, not the C boundary. Prototype is left dormant (hasattr-guarded, unused by server.py).

## Candidate-cap sweep (2026-08-26) — full coverage is NOT worth it; edge window is counterproductive

Motivated by "consider at least almost all candidates." Made `cat_limit` (per-category cap) and the edge-sampling window settings-driven (override-only keys `candidateCatLimit` / `candidateEdgeWindow`, absent by default so dynamic `int(limit)` behavior is preserved; validated override-only in `validate_settings_patch`). 6 × 500-ep runs (seed 42, ANY·mixed·4·120, lr 0.001) in an isolated worktree at `07195f5d`; results in `benchmarks/run_results/cap_*.json`; harness args `--cat-limit` / `--edge-window`.

**Determinism first (a correction to earlier numbers):** `cap_base` ≡ `cap_base2` bit-for-bit across all 500 eps. The tree is deterministic at scale. ~~The earlier `free_wins`/`ab_in` summaries (mean 39.88 / final-50 44.49 / placements 35.7) do NOT reproduce on `07195f5d`~~ — **SUPERSEDED (corrected by § "LR schedule + ratio clip"): this claim was WRONG.** The mismatch was the **learning rate**, not tree drift: `free_wins`/`ab_in` ran at `lr=0.001`, while `cap_base` ran at the harness default `lr=0.003`. On `07195f5d` at `lr=0.001`, the quality metrics reproduce **exactly** (mean 39.88 / final-50 44.49 / fill 43.4% / placements 35.7). The "divergence at ep 3 (placements 10 vs 9)" was likewise the LR difference. `cap_base` is the valid baseline **for `lr=0.003`**, not a refutation of the `free_wins` numbers.

**Why the mean is 29.5 and not 39.9:** at the harness default `lr=0.003` the trajectory has a **deterministic mid-run volatility/collapse** — eps ~200–350 swing wildly (single eps from −29 to +64; 25-ep window mean dips to ~3). This is the **known A2C-at-0.003 instability** (the earlier "0.003 collapses ~ep175, 0.001 is stable" finding), not generic site volatility. It dominates every mean-score comparison **at 0.003**; at `lr=0.001` the same tree is stable at ~40 (see § "LR schedule + ratio clip").

**Results (delta vs `cap_base`):**

| config | cat | edge | mean Δ | final-50 Δ | RSS Δ | wall Δ |
|---|---|---|---|---|---|---|
| `cap_base` | 12 | 12 | 0 | 0 | 0 | 0 |
| `cap_cat24` | 24 | — | **+3.71** | −8.99 | +17% | −9% |

| `cap_edge24` | — | 24 | −2.73 | −7.61 | +32% | −14% |

1. **`cat_limit` is the only lever with quality upside.** `cat24` gives the best mean boost (+3.7) but the late-training trajectory still collapses (final-50 −9). `cat48` is the cheap balanced option (+1.7 mean, +0.8 final-50) for +13% RSS. Consistency check: `cat24` ≡ `cat48` for eps 1–142, diverging only at ep 143 when sites get dense enough to exceed 24 valid candidates — the cap threading works exactly as intended.
2. **Widening the edge window is strictly negative.** `edge24`/`edge48` both lower mean AND final-50 (−2.4 to −11.6) at +26–32% RSS. More exposed edges feed the policy candidates it doesn't use well. Reject this direction.
3. **Full coverage (`wide48`) inflates the mean by dodging the collapse, not by better plans.** Its trajectory avoids the 250–400 dip (52.75 / 51.26 at eps 300/400) — but it costs **+72% wall time and +47% RSS** (candidate-gen/step roughly doubles 0.0042→0.0080 s, confirming candidate breadth is the cost driver), and it still drops late (final-50 −3.1; ep-500 dips to 21.97). The instability shifts rather than disappearing.
4. **Verdict:** considering "almost all candidates" is **not worth the cost**. The break-even is negative — full coverage buys a mean-score artifact from collapse-dodging, not robust final quality. The RL volatility (not candidate coverage) is what limits plan quality.

**Recommended:** take `candidateCatLimit=48` as a cheap, balanced default if anything; reject edge-window widening. Next lever for quality is the collapse itself (LR scheduling / mild ratio clip / multi-seed), not candidate breadth. — **DONE (2026-08-26):** the collapse was the `lr=0.003` default; cosine+clip or plain `lr=0.001` removes it (see next section).

## LR schedule + ratio clip — the collapse is the 0.003 default (2026-08-26)

Discovered en route that `cap_base` ran at the **harness default `lr=0.003`** (`default_settings()` in `benchmark_300_episodes.py` never overrides `learningRate`), so the "mid-run collapse" is the known A2C-at-0.003 instability. Tested two stabilizers, settings-driven and **override-only** (keys `lrSchedule` ∈ constant|cosine|linear, `lrFloor`, `lrHorizon`, `ratioClip`; absent from `DEFAULT_SETTINGS`, whitelisted in `validate_settings_patch` so defaults stay bit-identical — verified edited == pristine for eps 1–10). 5 × 500-ep runs (seed 42, ANY·mixed·4·120) on an isolated worktree at `07195f5d`; results in `benchmarks/run_results/lr_*.json`; harness args `--lr-schedule` / `--lr-floor` / `--lr-horizon` / `--ratio-clip`; analyser `analyze_lr_clip.py` (worktree).

| run | lr | clip | mean | final-50 | fill-50% | place/ep | wall | RSS |
|---|---|---|---|---|---|---|---|---|
| `cap_base` | 0.003 const | — | 29.50 | 39.70 | 37.0 | 30.9 | 11.0 min | 1100 MB |
| `lr_0001` | 0.001 const | — | 39.88 | 44.49 | 43.4 | 35.7 | 9.0 min | 1489 MB |
| `lr_cosine` | 0.003→0.001 | — | 40.72 | 40.66 | 41.9 | 37.6 | 7.8 min | 1610 MB |
| `lr_clip` | 0.003 const | ε=0.2 | 37.21 | **26.86** | 26.4 | 36.2 | 6.6 min | 1540 MB |
| **`lr_cosine_clip`** | 0.003→0.001 | ε=0.2 | **41.30** | **45.09** | 42.8 | 37.5 | 7.8 min | 1607 MB |

**Findings:**
1. **`lr=0.003` is a harmful default.** On the *same tree*, constant `lr=0.001` reproduces the `free_wins`/`ab_in` quality numbers **exactly** (39.88 / 44.49 / 43.4% / 35.7 placements) with **no collapse** and **−20% wall** (9.0 vs 11.0 min). The earlier "tree drift" explanation of the `free_wins` mismatch was wrong — it was the LR. **This corrects the cap-sweep § above.**
2. **Cosine + ratio clip (ε=0.2) is the winner**: mean **41.30** (+11.8 vs 0.003), final-50 **45.09** (+5.4, highest), smoothest trajectory (ep400 48.1, ep500 48.2), −26% wall. `lr_cosine_clip` ≡ `lr_cosine` bit-for-bit through ep 350, diverging only at 400 — the clip binds exactly when ratios leave [0.8, 1.2], which is when cosine alone starts wobbling (ep500 36.5 vs 48.2). The schedule avoids the mid-run burst; the clip prevents the late breakdown. **They complement.**
3. **Ratio clip alone at 0.003 is a reject**: it *defers* the collapse from eps 250–300 to eps 400–500 (final-50 26.86, fill 26.4% — worst final in the matrix). Bounding π/μ can't stop high-LR overshoot from accumulating; it just delays the burst.
4. **Cost**: the stable runs use more RSS (1489–1610 vs 1100 MB) because they place denser plans (35.7–37.5 placements/ep) → more cached geometry — the workload-density effect, not a leak. All four stable configs are *faster* wall-clock than 0.003 (6.6–9.0 min).
5. **Determinism**: `lr_cosine` and `lr_cosine_clip` share an identical prefix (eps 1–350) on the same tree — further evidence the tree is deterministic and the clip engages deterministically.

**Recommended:** the highest-value, lowest-complexity fix is **benchmarking/running with `lr=0.001`** (or flipping the default): reproduces the `free_wins` stability for free. If the small extra quality is wanted, adopt **cosine 0.003→0.001 with `ratioClip=0.2`** — settings-driven and default-neutral, so it changes nothing until enabled. Both are single-seed (`seed=42`); **multi-seed still deferred** — the +1.4 mean / +0.6 final-50 edge of cosine+clip over constant 0.001 is within single-seed volatility and should be confirmed across seeds before committing.

## Open questions / recommended order

- **Speed (highest value)**: candidate-gen breadth is the real cost. Options, roughly by risk:
  1. *Safe-cheap*: de-duplicate the identical `G.translate_polygon` call — **DONE** (no measurable effect, as expected).
  2. *Medium*: hoist the candidate `_native_polygon_signature`/`_packed_polygon_from_signature` OUT of the per-pair overlap loop (currently rebuilt once per placed poly per candidate). Marginal (overlap SAT is only ~7µs/candidate).
  3. *Medium*: attack the `_nearby_placement_ids` spatial query + anchor-loop breadth — the actual Python-side cost. Any change to breadth/count **changes RL coverage**, so needs the standard protocol.
  4. *Medium*: cap total anchors/step with an explicit budget to kill the 4–6s slow-tail spikes (changes distributional tail, not the mean).
- **Ratio clip**: answered by § "LR schedule + ratio clip" — a clip alone at constant 0.003 only *defers* the collapse (final-50 drops to 26.9); the effective combination is clip + cosine schedule (final-50 45.1).
- **Multi-seed**: all comparisons are single `seed=42`; both algorithms are volatile on mixed sites (milestones swing ±15 pts). The cap sweep is single-seed too; the volatility means any one run's deltas could flip on another seed — read the sweep as directional, not exact.

Diagnostics: `benchmarks/diag_memory.py` (RSS + native-buffer cache sizes), `benchmarks/micro_bench_batch_overlap.py` (per-pair vs batch); profile source is the per-episode `metrics["performanceTimings"]`.
